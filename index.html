1.Co budujemy

System, do którego wysyłasz zadanie przez HTTP, dostajesz numer zadania, a po chwili odbierasz wynik. Ciężka praca dzieje się w tle, na wielu workerach naraz.

W jednym zdaniu: klient wysyła POST /jobs, API zapisuje zadanie w bazie i wrzuca je do kolejki, worker je liczy, a klient pyta GET /jobs/{id} o status i wynik.

✅ Co będzie działać

  • 3 endpointy HTTP
  • 2 typy zadań: sum, csv_stats
  • N workerów liczących równolegle
  • Statusy i wyniki w PostgreSQL
  • Ponawianie nieudanych zadań
  • Skalowanie workerów przez Helm

🎓 Czego się nauczycie

  • Konteneryzacji (multi-stage build)
  • Komunikacji asynchronicznej
  • Kubernetes: Deployment, Service, Secret
  • Helm: chart + values
  • Terraform: stan i plan
  • Podstaw niezawodności (ack, retry)

🚫 Czego nie będzie

  • Frontendu ani UI
  • Logowania i użytkowników
  • AWS / chmury
  • Mikroserwisów i gRPC
  • Kafki, KEDY, Prometheusa na start
Najważniejsza zasada

Najpierw ma działać prosty przepływ end-to-end, dopiero potem dodajecie rzeczy. Lepiej oddać 100% prostego systemu niż 60% rozbudowanego.

Kelner nie czeka, aż kucharz skończy. Przyjmuje zamówienie i idzie dalej — dokładnie tak działa asynchroniczność.

Cykl życia zadania

  1. Klient wysyła zadanie. API sprawdza, czy dane są poprawne (np. czy numbers to tablica liczb).
  2. Powstaje rekord w bazie ze statusem pending i nowym UUID.
  3. API publikuje wiadomość do kolejki RabbitMQ i od razu odpowiada klientowi 202 Accepted z ID.
  4. Worker pobiera wiadomość. Zmienia status na processing i liczy wynik.
  5. Worker zapisuje wynik i ustawia status completed.
  6. Worker potwierdza wiadomość (ack) — RabbitMQ może ją usunąć z kolejki.
  7. Klient pyta o status i odbiera wynik.
pending→ processing→ completed lub →failed a przy retry: failed↩pending
Ważne dla beginnerów

TypeScript nie sprawdza danych w runtime. Typy znikają po kompilacji. Dlatego każde ciało żądania i każdą wiadomość z kolejki sprawdzamy biblioteką Zod. Typ = „co programista obiecuje”, Zod = „co faktycznie przyszło przez sieć”.

Dlaczego monorepo (npm workspaces)?

API i worker muszą używać tych samych typów i nazw pól. Wspólny pakiet packages/shared gwarantuje, że gdy ktoś zmieni format wiadomości, drugi projekt od razu pokaże błąd w edytorze.

To najtańszy sposób, żeby uniknąć „u mnie działa”.

Dlaczego Express, a nie Fastify/NestJS?

Express zna większość materiałów w internecie, ma najmniej „magii” i wystarcza w zupełności. NestJS wprowadza dekoratory, moduły i DI — za dużo pojęć na 2 tygodnie.

Zasada: najprostsze narzędzie, które spełnia wymagania.

4.Dlaczego TypeScript i jak go używamy

Jeden język w API i workerze. Typy pomagają pisać kod, ale nie zastępują walidacji — dane z sieci zawsze trzeba sprawdzić.

Jeden język

API i worker dzielą ten sam kontrakt w packages/shared. Zmiana pola w jednym miejscu od razu pokazuje błąd w drugim.

Typy + Zod

TypeScript sprawdza kod podczas pisania, Zod sprawdza dane w czasie działania. Potrzebujecie obu rzeczy.

Szybki start

tsx uruchamia TypeScript bez kompilacji, Vitest testuje w sekundę, a npm workspaces trzyma projekt w jednym repo.

Pułapka nr 1

TypeScript znika po kompilacji. Dane, które przychodzą z sieci, mogą być czymkolwiek. Jeśli zrobicie req.body as JobRequest, to nie jest walidacja — to kłamstwo. Zawsze JobRequest.safeParse(req.body).

Pułapka nr 2

W amqplib handler consume może być asynchroniczny, ale biblioteka nie czeka na Twój Promise. Zawsze opakowujcie ciało w try/catch i sami wołajcie ack / nack. Inaczej błąd zniknie po cichu.

5.Architektura

Komponenty — kto za co odpowiada

1. Job API apps/api

Robi: waliduje wejście, tworzy rekord, publikuje wiadomość, odpowiada na pytania o status.

Nie robi: nie liczy zadań, nie dotyka kolejki jako konsument.

Port: 3000

2. RabbitMQ infrastruktura

Robi: trzyma wiadomości, rozdaje je workerom, obsługuje retry i dead letter.

Nie robi: nie zna wyniku zadania — tylko je przekazuje.

Porty: 5672 (AMQP), 15672 (panel)

3. Worker apps/worker

Robi: pobiera wiadomość, wykonuje operację, zapisuje wynik i status.

Nie robi: nie wystawia HTTP, nie tworzy zadań.

Skala: 1..N replik, bez portu

4. PostgreSQL infrastruktura

Robi: przechowuje prawdę o zadaniu: typ, payload, status, wynik, błąd, czasy.

Nie robi: nie jest kolejką (to częsty błąd początkujących).

Port: 5432

Dlaczego baza i kolejka to dwie rzeczy

Kolejka jest do przekazywania pracy i jest ulotna. Baza jest do pamiętania stanu i jest trwała. Jeśli worker padnie w połowie, wiadomość wróci do kolejki, ale status w bazie dalej mówi prawdę o tym, co się stało.

7.Baza danych

Jedna tabela. Naprawdę. Nie potrzebujecie osobnej tabeli na wyniki ani na historię.

db/migrations/001_init.sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;  -- gen_random_uuid()

CREATE TABLE jobs (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type        TEXT NOT NULL,
  payload     JSONB NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending'
              CHECK (status IN ('pending', 'processing', 'completed', 'failed')),
  result      JSONB,
  error       TEXT,
  attempts    INTEGER NOT NULL DEFAULT 0,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at  TIMESTAMPTZ,
  finished_at TIMESTAMPTZ
);

CREATE INDEX jobs_status_idx ON jobs (status);
CREATE INDEX jobs_created_at_idx ON jobs (created_at DESC);

Dlaczego JSONB na payload i result?

Każdy typ zadania ma inny kształt danych. Jedna kolumna payload obsłuży i sumę, i CSV, bez migracji przy dodaniu nowego typu.

Walidację i tak robi Zod, więc baza nie musi znać wszystkich pól.

Dlaczego attempts?

Worker zwiększa licznik przy każdej próbie. Gdy osiągnie 3, zadanie idzie do failed i do kolejki dead letter — zamiast kręcić się w nieskończoność.

To zabezpieczenie przed „trującą wiadomością”.

Przykładowe zapytania

SQL — to, co naprawdę będziecie pisać
-- utworzenie zadania
INSERT INTO jobs (type, payload)
VALUES ($1, $2)
RETURNING id, status, created_at;

-- pobranie statusu
SELECT id, type, status, result, error, created_at, finished_at
FROM jobs
WHERE id = $1;

-- zajęcie zadania przez workera (idempotentnie!)
UPDATE jobs
SET status = 'processing', started_at = now(), attempts = attempts + 1
WHERE id = $1 AND status = 'pending'
RETURNING id;

-- zapis wyniku
UPDATE jobs
SET status = 'completed', result = $2, finished_at = now()
WHERE id = $1;
Sztuczka, którą warto zapamiętać

UPDATE ... WHERE id = $1 AND status = 'pending' RETURNING id to jednoczesne „sprawdź i zajmij”. Jeśli RabbitMQ dostarczy tę samą wiadomość dwa razy, drugi worker dostanie rowCount = 0 i po prostu potwierdzi wiadomość bez liczenia. To jest cała idempotencja, jakiej potrzebujecie.

8.RabbitMQ i niezawodność

Trzy kolejki

KolejkaDo czegoUstawienia
jobsNormalna pracadurable, wiadomości persistent
jobs.retryPonowienie po błędziex-message-ttl = 10000, dead-letter z powrotem do jobs
jobs.deadZadania po 3 nieudanych próbachdo ręcznego obejrzenia w panelu

Zasady, które muszą być spełnione

  1. Ack dopiero po zapisie do bazy. Jeśli potwierdzicie wiadomość przed UPDATE, a baza padnie — zadanie zniknie na zawsze.
  2. Prefetch = 1. Worker bierze jedno zadanie naraz. Prościej i sprawiedliwiej.
  3. Błąd = retry, nie nack(requeue: true). Natychmiastowe requeue tworzy pętlę, która zjada CPU, gdy zadanie jest trwale zepsute.
  4. Po 3 próbach → failed + dead letter. Zapisujemy treść błędu w kolumnie error.

Jak wygląda retry w praktyce

  1. Worker łapie wyjątek. Nie potwierdza „sukcesu”.
  2. Sprawdza attempt. Jeśli mniejszy niż 3 — publikuje kopię wiadomości do jobs.retry z attempt + 1 i dopiero potem robi ack oryginału.
  3. Kolejka retry trzyma wiadomość 10 sekund, po czym sama przekazuje ją z powrotem do jobs.
  4. Po trzeciej porażce worker ustawia status failed, zapisuje błąd i publikuje do jobs.dead.
Czego nie obiecujecie

Nie ma „dokładnie jednego” przetworzenia. RabbitMQ może dostarczyć wiadomość dwa razy. Wasza obrona to idempotentny UPDATE ... WHERE status = 'pending'. Na prezentacji mówcie o tym głośno — to pokazuje zrozumienie tematu, nie słabość.

apps/worker/src/consumer.ts — szkielet
import type { Channel, ConsumeMessage } from "amqplib";

export async function startConsumer(channel: Channel) {
  await channel.prefetch(1);

  await channel.consume("jobs", async (msg: ConsumeMessage | null) => {
    if (!msg) return;

    try {
      const job = JobMessage.parse(JSON.parse(msg.content.toString()));

      // "sprawdź i zajmij" — ochrona przed duplikatem
      const claimed = await pool.query(
        `UPDATE jobs SET status = 'processing',
                          started_at = now(),
                          attempts = attempts + 1
         WHERE id = $1 AND status = 'pending'
         RETURNING id`,
        [job.jobId],
      );

      if (claimed.rowCount === 0) {
        channel.ack(msg); // już zrobione albo w toku
        return;
      }

      const result = await runHandler(job);

      await pool.query(
        `UPDATE jobs SET status = 'completed', result = $2, finished_at = now()
         WHERE id = $1`,
        [job.jobId, result],
      );

      channel.ack(msg);
    } catch (err) {
      await handleFailure(channel, msg, err);
    }
  }, { noAck: false });
}

Te cztery pliki to 80% projektu. Reszta to ich odmiany.

11.1 Wspólny kontrakt

packages/shared/src/contracts.ts
import { z } from "zod";

// --- payloady poszczególnych typów zadań ---
export const SumPayload = z.object({
  numbers: z.array(z.number().finite()).min(1).max(10_000),
});

export const CsvPayload = z.object({
  csv: z.string().min(1).max(200_000),
});

// --- żądanie HTTP: type decyduje o kształcie payloadu ---
export const JobRequest = z.discriminatedUnion("type", [
  z.object({ type: z.literal("sum"), payload: SumPayload }),
  z.object({ type: z.literal("csv_stats"), payload: CsvPayload }),
]);

export type JobRequest = z.infer<typeof JobRequest>;
export type JobType = JobRequest["type"];

// --- wiadomość w RabbitMQ ---
export const JobMessage = z.object({
  version: z.literal(1),
  jobId: z.string().uuid(),
  type: z.enum(["sum", "csv_stats"]),
  payload: z.record(z.string(), z.unknown()),
  attempt: z.number().int().min(1).max(3),
});

export type JobMessage = z.infer<typeof JobMessage>;

z.infer tworzy typ TypeScript ze schematu. Nie piszecie typu drugi raz — jedno źródło prawdy. Gdy zmienicie schemat, edytor od razu pokaże, gdzie kod się zepsuje.

11.2 Endpoint POST /jobs

apps/api/src/routes/jobs.ts
import { Router } from "express";
import { JobRequest } from "@jobs/shared";
import { pool } from "../db.js";
import { publishJob } from "../queue.js";

export const jobsRouter = Router();

jobsRouter.post("/jobs", async (req, res) => {
  const parsed = JobRequest.safeParse(req.body);

  if (!parsed.success) {
    return res.status(400).json({
      error: "invalid_request",
      details: parsed.error.issues,
    });
  }

  const job = parsed.data;

  const { rows } = await pool.query(
    `INSERT INTO jobs (type, payload)
     VALUES ($1, $2)
     RETURNING id, status`,
    [job.type, job.payload],
  );

  const created = rows[0];

  await publishJob({
    version: 1,
    jobId: created.id,
    type: job.type,
    payload: job.payload,
    attempt: 1,
  });

  return res.status(202).json({ id: created.id, status: created.status });
});

jobsRouter.get("/jobs/:id", async (req, res) => {
  const id = req.params.id;

  if (!/^[0-9a-f-]{36}$/i.test(id)) {
    return res.status(400).json({ error: "invalid_id" });
  }

  const { rows } = await pool.query(
    `SELECT id, type, status, result, error, created_at, finished_at
     FROM jobs WHERE id = $1`,
    [id],
  );

  if (rows.length === 0) {
    return res.status(404).json({ error: "not_found" });
  }

  const row = rows[0];
  return res.json({
    id: row.id,
    type: row.type,
    status: row.status,
    result: row.result,
    error: row.error,
    createdAt: row.created_at,
    finishedAt: row.finished_at,
  });
});

11.3 Publikowanie do kolejki

apps/api/src/queue.ts
import amqp from "amqplib";
import type { JobMessage } from "@jobs/shared";

let channel: amqp.Channel;

export async function connectQueue(url: string) {
  const conn = await amqp.connect(url);
  channel = await conn.createChannel();

  // kolejki muszą istnieć, zanim ktoś opublikuje
  await channel.assertQueue("jobs", { durable: true });
  await channel.assertQueue("jobs.retry", {
    durable: true,
    arguments: {
      "x-message-ttl": 10_000,
      "x-dead-letter-exchange": "",
      "x-dead-letter-routing-key": "jobs",
    },
  });
  await channel.assertQueue("jobs.dead", { durable: true });
}

export async function publishJob(message: JobMessage) {
  channel.publish(
    "",                 // domyślny exchange
    "jobs",             // routing key = nazwa kolejki
    Buffer.from(JSON.stringify(message)),
    { persistent: true, contentType: "application/json" },
  );
}

11.4 Handler zadania

apps/worker/src/handlers/sum.ts
import type { JobMessage } from "@jobs/shared";

export function runSum(job: JobMessage) {
  const numbers = job.payload.numbers;

  if (!Array.isArray(numbers)) {
    throw new Error("payload.numbers must be an array");
  }

  const sum = numbers.reduce((acc, n) => acc + Number(n), 0);
  return { sum };
}
Dobra praktyka

Handler jest czystą funkcją — dostaje dane, zwraca wynik, nic nie wie o bazie ani o RabbitMQ. Dzięki temu test jednostkowy to trzy linijki, bez Dockera.

13.Kubernetes i Helm

Kolejność pracy

  1. kind create cluster — klaster jednorazowy, tworzony CLI, nie przez Terraform.
  2. Obrazy do klastra — docker build, potem kind load docker-image. Bez rejestru, bez chmury.
  3. Surowy YAML — najpierw ręcznie: Deployment, Service, Secret. Zrozumcie każdy zasób.

19.Scenariusz demo (7–8 minut)

Przygotowanie 15 minut przed

Klaster utworzony, obrazy wgrane, terraform apply wykonany, terminal powiększony, czcionka 16 px, panel RabbitMQ otwarty w drugiej karcie. Nie budujcie obrazów na żywo.

  1. Pokaż architekturę (30 s). Jeden slajd: klient → API → kolejka → workery → baza. Powiedz, że to system asynchroniczny, więc API nie czeka na wynik.
  2. Pokaż, że nic nie działa (15 s). kubectl get pods -n jobs → pusto. To buduje kontrast.
  3. Deploy jedną komendą (60 s). W infra/terraform: terraform apply -auto-approve. Potem kubectl get pods -n jobs -w. Skomentuj: „Terraform tworzy namespace i instaluje Helm chart”.
  4. Wyślij zadanie (30 s). curl z sum. Pokaż odpowiedź 202 i ID. Od razu GET — status pending.
  5. Pokaż wynik (20 s). Po 2 sekundach GET → completed, {"sum":60}.
  6. Skala (90 s). ./scripts/demo.sh 100. W drugim terminalu kubectl get pods -n jobs — 3 workery. W panelu RabbitMQ widać kolejkę malejącą. Potem kubectl logs -f z dwóch podów obok siebie — widać, że pracują równolegle.
  7. Awaria (90 s). kubectl delete pod -n jobs <worker-pod>. Pokaż, że Kubernetes tworzy nowy pod i że żadne zadanie nie zostało w pending. To najważniejszy moment prezentacji.
  8. Skalowanie (60 s). terraform apply -var="worker_replicas=5". kubectl get pods → 5 podów. Wyślij 20 zadań, pokaż szybsze opróżnianie kolejki.
  9. Podsumowanie (30 s). Czego się nauczyliście: kontenery, kolejki, orkiestracja, infrastruktura jako kod. Wspomnijcie o ograniczeniach (brak exactly-once, brak auth).

Plan B, gdy coś padnie

  • Klaster nie wstaje? Miejcie nagranie 2-minutowego demo (backup).
  • Terraform się wysypał? helm install ręcznie — pokażecie, że chart działa.
  • Brak internetu? Wszystkie obrazy wgrane wcześniej do kind.
  • Projektor nie widzi terminala? Zwiększcie czcionkę i użyjcie ciemnego motywu.

for i in $(seq 1 100); do

done
